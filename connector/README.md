# Диагностический соединитель 1С

Первый безопасный этап подключения «Хлеб.Приход» к локальной базе 1С.

## Что делает

- обращается только к локальной публикации OData;
- читает техническое описание доступных объектов (`$metadata`);
- сохраняет `diagnostics/metadata.xml` и `diagnostics/summary.json`;
- не читает товарные значения, не создаёт документы и не изменяет базу;
- не сохраняет имя пользователя или пароль.

## Запуск на магазинном компьютере

1. Распаковать архив в отдельную папку.
2. Дважды открыть `start-check.cmd`.
3. Оставить адрес `http://localhost/khleb1c/odata/standard.odata`.
4. Ввести имя отдельного пользователя интеграции и его пароль.
5. Нажать `Run read-only check`.
6. После сообщения `Success` передать папку `diagnostics` разработчику.

Администраторские права не требуются. Рабочую 1С можно оставить открытой.

## Сопоставление тестовых накладных

После успешной диагностики запустите `start-catalog-match.cmd`.

Этот тест:

- только читает минимальные поля номенклатуры и контрагентов;
- сохраняет только хлебные позиции и поставщиков «Мельник»/«Витязь»;
- создаёт папку `catalog-match` с двумя CSV-файлами и сводкой;
- не сохраняет пароль и не изменяет данные 1С.

Полученные папки `catalog-match` и `miller-history` содержат данные вашей 1С,
поэтому Git их игнорирует. Они должны оставаться только на рабочем компьютере.

## Локальная конфигурация бизнес-данных

Реальные GUID, выбранный исходный документ и состав тестовой накладной нельзя
публиковать в репозитории. После выгрузки кандидатов:

1. Скопируйте `business-data.example.json` в `business-data.local.json`.
2. Заполните `supplierLabel` и `counterpartyKey` по файлу
   `catalog-match/supplier-candidates.csv`.
3. При необходимости укажите номер или дату исходной накладной. Если оставить
   их пустыми, подготовительная проверка выберет последнюю накладную поставщика с товарами.
4. После безопасной выгрузки `test-write-preflight/source-document.json` заполните
   раздел `testInvoice`: GUID справочников и строки товаров.

`business-data.local.json` игнорируется Git. Не добавляйте его принудительно и не
отправляйте содержимое в публичные чаты или репозитории. Скрипт записи проверяет,
что все обязательные GUID заполнены, суммы считает сам и не принимает маркер из шаблона.

## Подготовка первой записи в тестовую копию

После создания отдельной базы `C:\Baze_Test_Hleb` и публикации
`http://localhost/khleb1c_test/odata/standard.odata` запустите
`start-test-write-preflight.cmd`.

Эта подготовительная проверка:

- использует фиксированный адрес только тестовой публикации;
- читает метаданные и полную структуру накладной выбранного в локальном файле поставщика;
- ищет указанный локально номер или дату, а без них — последнюю накладную с товарами;
- сохраняет отдельный список просмотренных документов для проверки их номеров;
- создаёт папку `test-write-preflight` с XML, JSON и сводкой;
- содержит бизнес-значения исходной накладной, но не содержит пароль;
- не отправляет запросы записи и не изменяет ни тестовую, ни рабочую базу.

## Первая тестовая запись

После анализа папки `test-write-preflight` запустите
`start-test-create-unposted.cmd` только на магазинном компьютере.

Соединитель:

- использует фиксированный адрес `khleb1c_test`;
- перед записью проверяет, что `default.vrd` указывает на `C:\Baze_Test_Hleb`;
- требует отдельного подтверждения пользователя;
- создаёт одну накладную из `business-data.local.json` с уникальным тестовым маркером;
- сохраняет документ непроведённым (`Posted = false`);
- перед созданием проверяет маркер и не создаёт дубль при повторном запуске;
- сохраняет запрос, ответ и сводку в папку `test-create-result` без пароля.

Если POST завершился, но проверка по маркеру не сработала, не запускайте запись
повторно. Поместите `test-verify-created.ps1` и
`start-test-verify-created.cmd` рядом с папкой `test-create-result`, затем
запустите CMD-файл. Проверка прочитает документ напрямую по `Ref_Key` из
`request.json` и не выполнит никаких запросов записи.
